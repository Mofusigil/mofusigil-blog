C++ RPC：把一次远程调用串起来

我在 2026 年 2 月至 3 月独立实现了一套 C++ 分布式 RPC 服务注册与调用系统。项目从学习 Raft 项目中的 RPC 模块开始，目标是理解本地服务怎样被注册、发布，再通过网络被其他节点调用。

相比单独学习某个库，我更想把网络、协议、服务发现和日志放进同一个项目里，沿着一次调用观察它们如何协作。

跳转到这里先看完整的链路

按职责拆开，主链路可以读成：

服务端注册服务 → 客户端发现服务
客户端序列化请求 → 网络传输 → 服务端解析与分发
业务处理 → 返回结果

我把实现分成四个重点：网络 I/O、通信协议、注册发现，以及运行日志。每个模块需要能单独理解，也需要在完整链路里有明确的位置。

跳转到这里网络 I/O：从连接走向业务

项目使用 Muduo 的 Reactor 模型，把网络 I/O 与业务逻辑解耦。学习这部分时，我关注的不只是某个接口怎么调用，而是数据从连接进入之后，在哪一层被接收、交给谁处理，以及业务模块需要知道哪些信息。

Linux Socket 编程、I/O 多路复用以及线程同步，都是理解这条链路的基础。把这些知识放在同一个项目里，能更清楚地看到它们之间的关系。

跳转到这里通信协议：序列化之外的边界

项目采用自定义通信协议，并结合 Protobuf 序列化请求与响应。处理 TCP 字节流中的消息边界，是这一部分的重要工作。

这里需要区分两件事：协议负责让接收方识别消息，序列化负责组织消息里的字段。把它们分开考虑，能够让网络层和具体业务的数据结构保持相对清晰的边界。

跳转到这里服务发现：把地址从调用里拆出来

我引入了 ZooKeeper 以及 Watcher 机制，用于动态服务注册与发现。服务提供方发布自身信息，调用方通过注册中心获取可用的服务信息。

这一步让我开始从“连接一个进程”转向“发现并调用一个服务”来思考系统。注册中心也带来了新的问题：服务信息什么时候更新，调用方怎样感知变化，以及连接异常时应该如何处理。这些都值得继续深入验证。

跳转到这里日志：让链路能被看见

项目集成 Glog 记录运行信息。跨越多个模块之后，一次失败可能发生在连接、消息解析、服务发现或业务处理阶段。日志需要帮助我辨认失败的位置，而不只是证明程序运行过。

跳转到这里下一步要验证的事

我希望继续完善的重点包括：

  • 在连接断开、服务变化和异常请求下，检查调用行为是否符合预期。
  • 把消息边界处理与服务发现流程拆成更容易验证的场景。
  • 补充可重复的测试与测量，再讨论吞吐、延迟和并发能力。

对我来说，这个项目是一条理解分布式系统的实践路径：把一个请求完整地送出去，再把沿途每个环节想清楚。
